## 4. Findings (ranked)

### M1 — Medium: capped-token handover checker does not establish exclusive Safe control

**Location:** `contracts/script/v3/DeployAPNTsCapped.s.sol:304` (`_checkTimelock`), especially `:310`–`:318`. Related trust-boundary requirement: `contracts/src/tokens/APNTsCapped.sol:17`–`:21`.

The checker requires the multisig to hold proposer/canceller/executor, the timelock to hold admin, and selected known addresses not to hold roles. It never checks all holders. Nevertheless `:318` calls its predicate “multisig-only.” A real OZ timelock with an additional address X (different from deployer/multisig/timelock/zero) holding admin and/or other roles satisfies every check here.

**Concrete failure scenario:** a supplied TIMELOCK retains X as external admin. Deployment and final `verify` accept it. X can grant itself proposer/executor/canceller without using a timelocked operation. Once token ownership has been accepted, X can schedule and later execute token-owner actions such as minter rotation or cap increases without Safe approval, or cancel Safe operations. The timelock still applies its then-current delay to scheduled token calls; this finding does **not** claim an immediate bypass of that delay. It breaks the intended exclusive governance authority and self-administration assumption.

**Suggested fix:** require a complete event-history holder-set check against an explicit expected manifest for this handover, using the current-chain/current-head verification approach already available to the governed upgrade flow, and verify the timelock implementation. Keep the distinction between off-chain preflight and on-chain enforcement explicit. Alternatively constrain the procedure to a newly constructed, verified timelock with fully known initial roles and verify subsequent grants/revocations. Add a negative test with an otherwise-correct timelock retaining an unlisted admin/proposer/executor. No such capped-deployment negative test was established in this review. The related `V2/D5bTimelockPreflight.t.sol` tests target the separate upgrade preflight, not this function.

### M2 — Medium: mandatory artifact gate rejects the newly supported capped aPNTs asset

**Location:** `contracts/script/checks/CheckDefaultArtifacts.s.sol:124`; failure branch in the same file `:292`–`:294` (`_clone`, declared at `:290`). Integration: `prepare-test:66` and `contracts/script/v3/UpgradeToV5_5_0.s.sol:377` (`queueAPNTs`).

The branch adds a direct-deployed `APNTsCapped` and an explicit migration entry point accepting it, but the generic checker unconditionally classifies config key `aPNTs` as an EIP-1167 clone of the old factory's `xPNTsToken`. A genuine capped token is a direct ERC20 contract, so `_eip1167Impl` returns zero and `_clone` records failure. The wiring check also requires SP.APNTS_TOKEN to equal config.aPNTs (`CheckDefaultArtifacts.s.sol:240`); leaving the old token in config is not a valid workaround.

**Concrete failure scenario:** execute the authorized capped-asset switch, then update config.aPNTs to the actual SP deposit asset. Mandatory T-4 checking fails with “not an EIP-1167 clone,” even when the capped token and its governance are correct. Leaving config unchanged fails wiring instead. `TestAccountPrepare.s.sol:91` also types the deposit token as legacy xPNTs and its preparation flow assumes legacy mint/administration privileges, so successful contract-level capped integration tests do not prove the advertised preparation path works. This is an operational compatibility failure, not evidence that capped-token deposits themselves are unsafe.

**Suggested fix:** explicitly discriminate the supported aPNTs families, verify direct `APNTsCapped` runtime/settings/roles through a reviewed artifact mapping, retain strict legacy clone checks, and adapt preparation/funding to the capped token's minter model. Do not bypass the checker. Add a regression that migrates a populated SP to capped aPNTs and runs the real generic verifier with the updated config. `Tok/APNTsCappedSPIntegration.t.sol` covers contract integration, but no test of this mandatory generic gate after migration was established.

### L1 — Low: lens may report sponsorship success after token SP rotation

**Location:** `contracts/src/paymasters/superpaymaster/v3/SuperPaymasterLens.sol:150`–`:173`; `contracts/src/tokens/v2/xPNTsTokenV2.sol:217`–`:228` and `:292`–`:302`.

**Concrete failure scenario:** user sets an explicit positive allowance cap for SP-A; its operator is funded/configured and user otherwise eligible. The token completes its approved/timelocked rotation to SP-B, while SP-A retains its operator configuration. Add a lens-vs-validation test after rotation, with both explicit-cap balance mode and credit fallback. Existing normal/low-gas lens agreement tests and token authority/rotation tests do not combine this sequence.

## 5. Adversarial checks and residual coverage limits

**Decision 1, reservation and settlement.** Token selection is bound in paymasterAndData; rate commitment is checked before reservation. SP verifies its operator balance before touching the token and falls back to credit only for the explicit INSUFFICIENT result. Lock records hold the original locker, reserved aPNTs and locked xPNTs; settlement caps charge to reservation and burns at the recorded lock ratio. The balance hook prevents transfers/burns that undercut locks. Credit admission checks debt + outstanding reservation + requested amount against the effective opt-in cap; settlement uses the admitted reservation without re-reading policy/tier. Old lockers may settle existing live records after rotation, while new reservations require current-SP authority. Stale releases are idempotent and blocked by transaction-live markers. These observations support the intended local invariants, not a proof over every execution.

**Decision 2, bounded allowance.** Explicit ERC20 allowance is consumed before bounded auto-allowance. The implicit remainder is charged upward in aPNTs and consumes per-spender and per-user counters; transfer destination is restricted for the implicit portion. Current/historical SPs cannot pull even with an explicit approval. Renewal requires no outstanding lock or credit reservation; SP renewal is K-bounded while user/account-authorized renewal is explicit. Disable/re-enable and remove/re-add preserve counters. Credit is separately consented and bounded; it does not consume the balance-mode auto-allowance, which is an intentional separate authority surface to assess operationally.

**Rounding.** Reservation pricing/fee and xPNT lock use ceiling rounding; partial settlement uses a ceiling of the recorded lock ratio and is capped by xLocked. Auto-allowance reporting floors its live conversion while spending charges ceiling aPNTs. Mint debt repayment floors the repayable aPNTs and ceilings burned xPNTs; explicit repayment floors debt reduction. No round-down undercharge in the new reservation/settlement paths was identified. Dust can favor charging within the admitted bound; this is not an exact live-rate settlement promise.

**Reentrancy and postOp failures.** SP validation, settlement, and token deposit/withdraw paths share the storage-chain guard. Token hot-path reservation/settlement has no untrusted callback; tier lookup is static and gas-capped. The ERC-1363 extension path updates transfer state before callback and guards its own callback entry. Signature actions validate the user's authority and consume nonce before action; no unrelated-user reentrancy escalation was identified. Settlement failures bubble: the implementation depends on EntryPoint v0.7 rolling back user execution while preserving validation reservations for later release. Tests exist for this behavior, but the rollback/gas-band claims were **not verified by execution here**. Release restores operator tokens, not the ETH spent from the EntryPoint deposit. Price, gas parameters and fee snapshots reduce mid-bundle repricing; forward/rollback context tests exist, but they do not authorize arbitrary older implementation contexts.

**Validation rules.** Source traversal of the new token lock/credit/self-renewal routes found no direct TIMESTAMP/NUMBER access in those function bodies; timestamp-dependent spend-rate-limit, governance and signature helpers live outside the intended validation paths. Token mutable lock/credit/cap cells use user-associated keying, including transient live markers. SP's own operator/in-flight/guard storage and external global reads rely on a properly staked paymaster. The GlobalTierSource route reaches Registry.getCreditLimit and its reputation/threshold table. The fixed core/extension split keeps admin fallback out of the explicit hot-path functions, but deployment still adds clone/proxy delegatecall frames and external identity/tier code. Exact ERC-7562 acceptance is **not verified**: no bundler simulation/opcode/storage trace or deployed-stake read was run. A caught EVM revert does not make a forbidden opcode acceptable to a bundler. Do not interpret static review as certification of every configured external identity registry/tier source.

**Governance.** Owner authority remains a substantial trust boundary: UUPS upgrades can replace enforcement; allowlist governance approves address/hash keys and must avoid upgradeable-proxy runtime hashes for spender/tier approval; community owners can mint/change rates within enforced bounds and switch credit/SP policies through stated gates. The pending-owner namespace and upgrade block prevent carrying a stale nomination through the supported rollback path. Safe/timelock role exclusivity and completion of ownership acceptance require independent live verification; M1 shows one procedure does not yet establish that claim.

Coverage is partial rather than universal: the named regression suites target the major new reservation, bounded-allowance, failure, governance and upgrade behaviors, but not every retained admin/view helper or every cross-product of rotation, gas, price, cap, ownership and bundle state. Finding-specific missing regressions are identified above. No tests were edited or reviewed for their own correctness.
