### 1.1 trace 是怎么拿到的

每个 bundler 都不直连 anvil，而是连 `script/b-layer/g1-proxy.mjs`（透明 JSON-RPC 代理）。代理遇到带 JS tracer 的
`debug_traceCall`（也就是 bundler 的 ERC-7562 验证模拟）时：

1. **先**把同一个请求（同一个 call 对象、同一个 block、同一组 `stateOverrides`，只把 `tracer` 换成我们的）发给 anvil，
   得到我们自己的 trace。这时 bundler 还在等回应，不会发交易，所以状态与 bundler 看到的一致；
2. 再原样转发 bundler 的请求，原样返回结果；
3. 把「用例标签 + 请求（tracer 代码换成 sha256）+ bundler 自己 tracer 的结果 + 我们 tracer 的结果」追加到 jsonl。
   bundler 的 tracer 代码本身也存了一份（`cases/*-bundler-tracer-*.js`）。

两个 bundler 的模拟形态不同：Rundler 对 EntryPoint 地址 `debug_traceCall`，用 `stateOverrides` 把代码换成
EntryPointSimulations，调 `simulateValidation`（`0xc3bce009`）；Alto 调它自己部署的 PimlicoEntryPointSimulations
（`simulateEntryPoint` → `EP.delegateAndRevert` → DELEGATECALL `simulateValidationLast(ops[])`），并且把**内存池里同 sender
或同 paymaster 的待处理 op 排在前面一起模拟**。

我们的 tracer（`script/b-layer/g1-tracer.mjs`）与 bundler 的 tracer 的区别：把 SLOAD / SSTORE / TLOAD / TSTORE **分开**记
（两个 bundler 都按 OP-070 把 T* 并入读写），记录每个调用帧（类型、from、to、存储上下文、selector），按「调用者的存储上下文是
EntryPoint 的 CALL/STATICCALL」切出验证阶段（factory 由 `createSender` `0x570e1a36`、account 由 `validateUserOp`
`0x19822f7c`、paymaster 由 `validatePaymasterUserOp` `0x52b7512c` 识别），逐帧记禁用 opcode（TIMESTAMP、NUMBER、ORIGIN、
GAS 后面不跟 CALL、BALANCE、CREATE2 等），并收集所有 KECCAK256 的输入（≤ 160 字节）用于还原槽名。Alto 的模拟里排在前面的 op
不计入，只取**最后一个** op 的各阶段。

## 3. §3.4 逐行对照

脚本 `script/b-layer/access-check.mjs`，输入是代理存下的**我们的 trace**（与 bundler 同一请求），输出 `cases/access-check.json`
（每个 case 的第一次模拟带完整的逐槽表）和 `cases/access-check.txt`（计数）。

- **槽 → 名字**：存储布局来自 `forge inspect <C> storageLayout --json`（`cases/layouts/` 下 xPNTsTokenV2、SuperPaymaster、Registry）；
  mapping 槽用 trace 里收集到的 KECCAK256 原像递归还原（`keccak(key‖base)+n`，嵌套 mapping 逐层），动态数组用 `keccak(p)+i`，
  活标记用已知的三个 SEED 常量，ERC-1967 / OZ 命名空间槽用常量表。键里的地址还原成 `u`（本 op 的 sender）、`SP`、`operator` 等。
- **归类规则**（与 §2.3 逐行对应）：R1 只能是 SP 帧的**读**、且是 `SUPERPAYMASTER_ADDRESS / historicalSP[SP] / emergencyDisabled /
  exchangeRate / maxSingleTxLimit / creditPolicy / policyEpoch / creditTierSource / community` 所在的槽（打包槽按槽里所有变量标出）；
  R2 读写类必须最内层键 = sender（`_auto`、`spenderDisabled` 还要求外层键 = SP），只读类出现 SSTORE 即判清单外；R3 必须是 TSTORE
  且槽 = `keccak(u‖keccak(h‖LOCK_SEED|CREDIT_SEED))`；R4 只在账户阶段、只能是 6 个变量且最内层键 = sender；任何读写
  `_reentrancyStatus / usedOpHashes / spenderRateLimit / total*`、任何验证阶段帧里出现 TIMESTAMP / NUMBER / ORIGIN 都记为禁止项。
- **结果**：Rundler 34 次、Alto 36 次、altoMulti 36 次模拟，**清单外 0、禁止项 0**，其他禁用 opcode 0（B4 工厂阶段的 1 次 CREATE2 按
  OP-031 单独计为允许）。

## 4. 发现

### F1（高）同一 sender 的第 k 笔在 bundle 内失败 → Rundler 把 SP 封禁（ERC-7562 SREP-050）

- **现象**：B2b 三笔在提交时都被 Rundler 接受（已查证：Rundler 的首次验证和第二次验证都是逐笔针对同一区块状态进行的，不考虑同 sender 的其他待处理 op，源码见 `F1-investigation.md`），出块时第 3 笔在
  `handleOps` 估算里 `FailedOp(2, "AA34 signature error")`。Rundler 把 `AA30/AA31/AA33/AA34` 归为 paymaster 的责任
  （`crates/builder/src/bundle_proposer.rs:1149-1157`），整个 bundle 作废，paymaster 作为 rejected entity 从池中移除
  （`uo_pool.rs:145`），信誉按 SREP-050 直接设为 `ops_seen = 10,000`（`crates/pool/src/mempool/reputation.rs:239-242`，
  `bundle_invalidation_ops_seen_staked_penalty`）。读回：SP `opsSeen 0x2710 / opsIncluded 0xc / status 2 (BANNED)`；
  之后任意用户经这个 SP 的 op 都返回 `-32504 paymaster … throttled or banned`。**前两笔本来合法的 op 也一起被丢弃。**
- **根因**：SP 5.5.0 在验证期对用户余额加锁（`lockedOf[u]` 由同一 bundle 里前面的 op 写入），所以第 k 笔的验证结果依赖同一 sender
  前面几笔的验证。这不违反 ERC-7562 的存储规则（读写的都是与 sender 关联的槽，§3.4 为 0），但 ERC-7562 让已质押的 paymaster 为
  「首次验证通过、bundle 内失败」负责。
- **影响**：任何用户（无需恶意，快速连发几笔、余额只够前几笔即可）都能让共享 SP 在 Rundler 系 bundler（Alchemy 等）上被封禁，
  覆盖所有社区；攻击成本为 0（op 从未上链）。信誉按小时衰减，但可以反复触发。这是 SP 活性问题，不是资金安全问题。
- **Alto 不受影响的原因**：Alto 在提交时把同 sender / 同 paymaster 的待处理 op 排在前面一起模拟（`simulateValidationLast`），
  第 3 笔在提交时就被拒，不会进入 bundle。
- **可能的方向（供 DSR / 作者决定，本任务未改 src）**：① 我们自己的 SuperRelay（Rundler fork）把
  `--pool.same_sender_mempool_count` 设为 1，或在提交时对同 sender 的待处理 op 做累计模拟（运营层，只保护自有 bundler）；
  ② SDK / AirAccount 对同一 SP 只允许 1 笔在途 op（只约束诚实用户）；③ 合约层让第 k 笔的首次验证能「看见」前面的锁是做不到的，
  若要根治，只能让验证结果不依赖同 sender 其他 op 的验证写入（例如余额不足时不在验证期失败），这与 I9 / T-R14-02 的设计直接冲突，
  需要重新权衡。runbook 与 D7 在决定之前应把「单 sender 单在途 op」列为前提。

### F2（中）估算不能直接用：Rundler 不估 postOp，Alto 估出的 postOp 低于 SP 的下限

- Rundler v0.11.0 的 `GasEstimate` 结构只有 PVG / verif / call / pmVerif（`crates/types/src/user_operation/mod.rs:853-866`），
  **不返回 `paymasterPostOpGasLimit`**；不传时模拟用 0（`v0_7.rs:734` `unwrap_or_default()`）。这时 SP 在
  `pmPostOpGas < MIN_POST_OP_GAS` 处提前返回 sigFail，于是 **`paymasterVerificationGasLimit` 被估成 38,403**，而真实路径要
  198k–238k。SDK 若照用，op 会在 paymaster 验证里 OOG。
- Alto v1.2.5：返回 `max(传入值, 实测 × 倍数) × v7 倍数`。传 200,000 → 240,000（满足）；不传 → **114,560 < 200,000**，
  SDK 照用会被 SP 以 sigFail 拒绝（`SuperPaymaster.sol:1210`）。
- **结论**：SDK / D7 必须自己设 `paymasterPostOpGasLimit ≥ 200,000`（建议取 `max(估算值, 200,000)`），并且估算时总是带上
  这个值（否则 Rundler 的 pmVerif 估算走错路径）；pmVerif 也应设下限（实测 ≥ 238k，含 SP_RENEW / 信用路径）。

### F3（低，文档）§2.3 清单漏了 Registry 的几项全局读

B7 的分档源路径里 Registry 还读了：代理的 ERC-1967 implementation 槽、`levelThresholds.length`（6 次）和
`levelThresholds[0..4]`（`_levelForReputation` 的循环）。都是已质押 SP 帧里对非实体合约全局槽的**读**，STO-033 允许，
两个 bundler 都接受；但 §2.3 第 1 行只写了 `creditTierConfig`，应补上这三项（以及「代理的 implementation 槽」这一类）。
SP 自身的存储（包括 SP 的 `nonReentrant` 在验证期读写 `_status`）不在 token 清单的范围内，属于已质押实体的自有存储。

### F4（信息）Sepolia / OP 主网上的 SP 现有质押在 Rundler 上会被拒

B9 用的正是现网值 0.1 ETH / 86400 s：Rundler 拒绝，原因是 SP（因质押不足按未质押处理）读了 token 的 `exchangeRate`
（STO-033 需要质押）。runbook 5b（补到 ≥ 1 ETH）是必需的；Alto 在这件事上不可作为依据（D1）。
