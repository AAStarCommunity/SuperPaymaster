# D3 · M 层：迁移旧测试的断言做源码变异

> 分支 `feat/aoa-balance-mode-5.5.0`，基线 `093bf37e`。规范：[03-final-spec.md](03-final-spec.md)。上游交付记录：[D2-traceability.md](D2-traceability.md) §5（22 个文件的迁移，迁移组不能改 `src/`，新写的断言没做过变异）。
> 本层只改 `contracts/test/`，`contracts/src/` 零改动（每次变异后逐字节恢复并校验，见 §6）。

## 1. 范围

**被审对象**：`ffa027ff`、`6bca064d`、`fb06bd9e`、`da11016b` 四个迁移提交在 `contracts/test/` 里新增或改动的断言。

| 口径 | 数量 | 取法 |
|---|---|---|
| 新增/改动的断言行（`assert*` / `vm.expectRevert` / `vm.expectEmit` / `vm.expectCall`） | **360** 行，分布在 100 个函数里 | `git diff -U0 <c>^ <c> -- contracts/test` 的 `+` 行 |
| 被迁移触及的测试函数（函数体里有任一 `+` 行） | **119** 个 | 同上，按新文件的函数边界归属 |
| 22 个文件的基线 | 257 个测试全绿（本层之后 261 个，+4 个新测试） | `forge test --match-path '{…22 个文件…}'` |

**判定标准**（DSR 要求）："每个机制都要有指名的断言变红，而且要确认变异真的改变了目标场景的行为"。本文据此把结果分三档：

- **具名红**：失败信息是测试里写的那条断言的 message（或带选择器的 `expectRevert` 报的 "next call did not revert as expected" / "Error != expected error"），并且信息里的实际值与期望值不同 —— 这本身就证明变异在该场景里被执行、并改变了行为（没被执行的变异不可能改变一个等值断言的实际值）。
- **匿名红**：测试失败了，但失败信息是 `EvmError: Revert`、`panic: 0x11`、`NoLock()` 这类冒泡上来的 revert，没有落在任何一条断言上。变异确实触达了，但"是哪条断言在守这个机制"说不清。**第一轮里有 6 个变异只有匿名红，全部在 §4 加强后变成具名红。**
- **无红**：变异在全部 22 个文件上都是绿的。要么断言弱（加强），要么变异在这些场景里根本不触达/不可观测（§5 逐条写原因）。

## 2. 结果汇总

| 轮次 | 变异数 | 具名红 | 只有匿名红 | 无红 |
|---|---|---|---|---|
| 第 1 轮（迁移组原样的测试） | 99 | 82 | 6 | 11 |
| 第 2 轮（加强之后；99 + 新增 8 个变异） | **107** | **105** | **0** | **2** |

- 最终两个无红：`P_gas_bound`（迁移组的场景里 postOp 永远拿到 ≫ 80k gas，这个分支不会被执行；它由 v2 套件的 `test_B1_postOp_entry_gas_guard` 守着，见 D2 §4 #2）和 `P_live_off`（**等价变异**，任何可观测行为都不变，见 §5）。两者都不是迁移组断言所声称的机制。
- 119 个迁移触及的测试函数里，118 个至少被一个变异打红；剩下的 `DryRunValidation::test_DryRun_IsViewOnly_NoBalanceChange` 按构造不可判定（§5）。
- 变异分布：SuperPaymaster 75 个、SuperPaymasterLens 19 个、xPNTs v2（`xPNTsTokenV2` 11 个、`xPNTsV2Base` 2 个，只取迁移断言明确引用的 token 侧机制）13 个。
- 全量回归：Cancun **1522 通过 / 0 失败 / 49 跳过**；Prague **1431 通过 / 0 失败 / 21 跳过**；`git status --short contracts/src` 为空。

## 7. 对 src 的观察（本层不改 src）

没有发现 5.5.0 引入的源码缺陷。以下两点供参考：

1. **价格缓存从未初始化时 validate 是 revert 而不是 sigFail**：`_calculateAPNTsAmount` 在 `cachedPrice.price <= 0` 时 `revert OracleError()`，而 validate 在它之前没有检查价格。只在部署后、第一次 `updatePrice` 之前出现，且与 5.4.x 行为相同（不是本次回归）。lens 对同一状态返回 `STALE_PRICE`。若希望"所有拒绝都 fail closed"，可在 validate 里对 `price <= 0` 直接返回 sigFail —— 属于 SP 的设计选择，留给 SP 决定。
2. **`_setInflightLive(c.opHash, false)` 是无效果的一行**（见 §5 `P_live_off`）。保留无害；删掉可省少量 gas，但不影响任何性质。

另：写 R-2 新测试时第一次用"默认用户 + SP_RENEW 位"做场景，结果被接纳 —— 这是规范行为（`renewalMode` 默认 `SP_K`，见 spec 03 的 D-18 与 R4-H1），不是缺陷；测试改为先设 `ACCOUNT_ONLY` 再验证 A-5 的"INVALID_RENEWAL 整个验证失败、不转信用"。
